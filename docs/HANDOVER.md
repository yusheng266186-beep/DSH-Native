## 验证手段

**没有模拟器，没有真机调试回路。** 所有验证都靠下面这几种间接方式。
接手后请沿用，并继续补充。

### 能自动化的（每次构建都跑）

```bash
bash scripts/run_tests.sh     # 580 项纯逻辑断言
```

### 需要手工跑的

| 验证什么 | 怎么做 |
|---|---|
| **运行包完整性** | 拉线上清单，与本地逐分片比对 sha256 |
| **哨兵是否真实存在** | `tar --use-compress-program=unzstd -tf <分片>` 里找 |
| **补丁前提是否成立** | 从线上运行包提取目标文件，grep 匹配标记 |
| **生成的 YAML 是否合法** | 拿它**真的启动一次 DSH**，看插件是否被加载 |
| **归档能否正确解压** | 用 App 自己的 `unpack.js` 解压，与直接 tar 比对文件数 |
| **恶意备份包** | 构造带 `../` 的 zip，确认磁盘上**真的没有**多出文件 |

### 起一个临时 DSH 验证插件

```bash
export DSH_HOME=/tmp/probe
node --expose-internals <dsh>/lib/bin.js --profile web --no-open --port 3099
# 取日志里的 token，然后：
curl -sSL -o /tmp/index.html "http://127.0.0.1:3099/?token=<token>"
grep -o '<插件名>' /tmp/index.html      # 出现即说明插件生效
```

这个「检查首页里有没有插件名」的方法，是唯一能确认
bundle 类插件真的生效的方式。

## 8.1 构建与发布：现在全在 CI 上

本机（Android App 沙箱）**没有 JDK / aapt2 / d8 / apksigner**，
所以编译只能交给 CI。两个工作流：

| 工作流 | 触发 | 做什么 |
|---|---|---|
| `.github/workflows/build.yml` | 推送到 main（改到 src/tests/scripts/payload/icon）或手动 | 构建 + 全部断言 + 四道闸门 + 上传 APK 产物。**不发布** |
| `.github/workflows/release.yml` | **手动**（输入版本号） | 升版本号 → 构建 → 上传 Release → 验证两条下载路径 → 写 `latest.json` → 提交推送 |

`release.yml` 的输入：

* `version`（必填）：目标版本号
* `dry_run`：只升版本号 + 构建 + `git push --dry-run` 验权限，**不发布不提交**。发版前先跑这个
* `notes_file`：发布说明路径，默认 `release-notes/v<版本>.md`，没有就从上一个 tag 的 git log 生成
* `signer_ref`：**签名比对参考版本**，默认取最新发布版。**重发同一个版本号时必须显式指定**（例如换成已安装版本用的一致签名时）

### 注意事项（都踩过）

1. **`GH_TOKEN` 是必需的**：构建要从"上一个发布版"的 APK 里取内置负载（node + 10 个 .so，
   共 93MB，不在仓库里）。这一步曾用**未认证**的 GitHub API —— 它按 IP 限流 60 次/小时，
   而 CI runner 共享 IP，于是**同一份代码前一天能过、第二天失败**。现在优先走带 token 的 `gh`。
2. **build-tools 固定 34.0.0**：runner 预装了更新的版本，`sort -V` 会选中它。固定才可复现。
3. **`build_bootstrap.sh` 会 `cd "$DSH_BUILD_DIR"`**：3.4/3.45/3.46/3.5 四道闸门用的是相对路径。
4. **emoji 闸门是真的了**（3.46）：此前 `AGENTS.md` 声称"构建脚本里有检查"，实际**从未存在**，
   于是两处违例（`PluginSpecs.java`、`bump_version.sh`）挂了三天没人发现。

## 8.2 签名：这一类事故会直接让所有用户装不上

**事故经过**：仓库里的 `scripts/release.keystore` 是**第一版 PoC** 提交进来的
（证书 `OU=POC`），项目改用引导式架构后从未替换；而历次实际发布用的是构建容器里
**自动生成**的另一把（`OU=Bootstrap`）。两把并存、没人核对过 —— 直到用户点更新被系统拒绝：

```
安装失败(-7)：与已安装应用签名不同
```

只能卸载重装，而卸载会清掉应用私有目录里的**全部会话与 API 密钥**。

### 现在的防护（三层）

1. `scripts/check_signer.sh <APK 或 URL>`：核对"仓库密钥"与"已发布 APK 的签名"是不是同一把
2. `release.yml` **发版前强制**跑上面这个核对，不一致就停下
3. `build_bootstrap.sh` 在找不到密钥时**直接失败**，不再默默生成新密钥
   （确需新密钥必须显式 `DSH_ALLOW_NEW_KEYSTORE=1`，且会打印警告）

### 红线

**不要换签名。** 换签名 = 所有已安装用户必须卸载重装 = 丢会话与密钥。
CI 用的是仓库里那把，与线上已发布版本一致（证书 SHA-256 `9bf19e21…`）。

## 8.3 新增红线（这几轮的返工换来的）

| 红线 | 原因 |
|---|---|
| **任何会触发 `recreate()` 或 Activity 生命周期的逻辑，必须带防振荡三件套**：去抖复核、跨重建限流（计数存 prefs 而非实例字段）、超限硬停止 | 主题跟随曾按"每收到一次上报就重建"实现 → 页面重载会**先报旧主题再报新主题** → 无限重建。用户侧表现为"深浅反复横跳、应用不停重启"，**卸载重装也无效**（主题缓存存在应用数据里）。更讽刺的是当时加的限流器是**实例字段，每次重建都归零**——限流器被限流对象自己重置了 |
| **XML 注释里不能出现连续两个减号** | 写令牌名 `--dsw-alias-...` 进注释 → aapt2 报 `not well-formed (invalid token)`，构建失败。Java 检查覆盖不到资源，这类错误只能等 CI |
| **改颜色必须通过 `DshUi` 的方法** | 颜色原本是 `public static final int`，javac 会把值**内联**到每处调用点 —— 运行时改字段对已编译代码完全无效。深色模式因此不得不把 65 处调用点从字段改成方法 |
| **主题跟随的是 DSH 网页，不是 Android 系统** | DSH 有自己的 `ui-theme.preference`（light/dark/system），与系统深色**相互独立**。只跟系统会出现"网页黑、原生白卡片"的同屏割裂 |
| **注入脚本必须每次页面加载都执行** | 原来是"只注入一次"，而任何 reload 都会清空页面里的脚本 → 刷新后状态看板、任务通知、接口诊断**全部静默失效** |
| **多 agent / 多会话并行改这个仓库时，动手前先 `git fetch`** | 实测吃过亏：本地克隆落后 5 个提交，却以为读到的是当前状态 |
| **发布前必须拿到子任务的明确交回**，不能拿"文件多少秒没变"当完成信号 | 曾据此发布，而那个子任务当时仍在写；发布后文件又被改了 4 次 |

## 8.4 本地核验（没有 javac 时能做什么）

```bash
python3 scripts/check_java.py     # 1) javalang 语法解析 2) 跨类方法引用 3) 资源 XML 4) 三道闸门
```

* javalang 是**真正的 Java 解析器**，比数括号可靠得多；没装时第 1、2 步自动跳过
* **它只覆盖语法与引用，类型层面的错误只有 CI 的 javac 能发现**
* 不要用它替代 CI 绿灯

## 8.5 已知陷阱（继续补充）

1. **`values-night` 是半废件**：它最初为"让网页上报深色"而加，但主题后来改成跟网页走，
   于是它只剩"启动窗口不闪白"的作用 —— 而它的触发条件是**系统**深色，与主题来源不是一回事。
   **结果：DSH 设深色 + 系统浅色时，启动那一瞬间仍会闪白。未修。**
2. **主线程写日志已修但值得记住**：`onConsoleMessage` 是 UI 线程回调，而每条 `[dsh-api]`
   响应都要写日志 —— 实测日志里 **72% 的字节**来自这类行。曾经每来一个请求主线程就做一次
   同步文件写。现在改为有界队列 + 后台写盘（队列满则丢弃并记录丢弃条数）。
3. **`[dsh-theme]` / `[dsh-sess]` / `[dsh-dom]` / `[dsh-native]` 这些注入标记会被 App 拦截消费**，
   **不写进日志**（避免刷爆）。排查时别去日志里找它们。
4. **会话列表的 `running` 是判断"有没有任务在跑"的唯一权威依据**。曾经：
   * 从被 `slice(0,700)` 截断的响应里数 `running:true` → 漏数 → 误报**空闲**
   * 改用页面按钮（"停止生成"/"发送消息"）判断 → 误命中 → 状态**钉死**在运行中
   现在：页面侧解析**完整 JSON** 上报计数 + **每 5 秒重放**该只读 RPC 保证证据新鲜；
   超过 90 秒无数据报"状态未知"，而不是把旧状态挂着。
5. **不要用页面的按钮文案判断运行状态**：文案一变就失效，且误命中时优先级最高会盖掉正确信号。

这几轮改动量很大，但**验证强度差别极大**，必须分清：

| 事项 | 验证到哪一步 |
|---|---|
| 编译、全部断言、四道构建闸门 | **CI 每次提交都跑**，可信 |
| 签名一致性与两条下载路径 | 每次发版强制核对，可信 |

| **0.24.0 那一批的全部改动**（对话框动画、顶部进度条、按钮禁用态与 44dp、列表分批渲染与遮罩、编辑器未保存守卫/原子保存/行号索引、四个面板的异步生命周期、无障碍） | **只验证到"能编译 + 断言通过"**，没有一条做过真机行为验证 |

**建议的集中验收清单**（一次操作即可覆盖大部分未验证项）：

1. 设置 → 浏览文件 → 进一个大目录：看分批渲染、加载遮罩、行高
2. 打开一个文本文件改一下再按返回键：应问「继续编辑 / 丢弃 / 保存」
3. 打开日志面板：应显示「正在读取日志…」并自动滚到最底部
4. 在 DSH 设置里切一次深色：原生应跟着变，且**只重建一次**
5. 跑一个任务：通知栏状态应准确、顶部出现加载进度条

## 8.7 用户数据与恢复

* 用户数据在 `<root>/.dsh`（会话、`settings.yaml`、`.credentials.yaml`、附件）。
  **卸载会清掉全部**，而换签名必须卸载 —— 这是"不要换签名"的根本原因。
* 备份方式：`tar -cf /sdcard/DSHNative/backup/dot-dsh.tar -C <root> .dsh`
  （`/sdcard` 是 FUSE，**不支持符号链接**，所以必须用 tar 而不是 `cp -r`）
* 恢复：`tar -xf <备份> -C <root>`
