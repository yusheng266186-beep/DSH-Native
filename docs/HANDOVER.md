## 待办

### 优先级高

**1. 真机验证从未做过**

代码里有一套布局自检（`FileBrowser.reportLayout`），
但需要用户在手机上操作才会触发。**到目前为止没有任何一次真机验证记录。**

具体做法：让用户打开「设置 → 文件」，然后分享日志里的
`布局自检: …` 那一行。这条数据能一次性确认所有列表类界面有没有
挤压、溢出、遮挡问题。

**2. 逐条审计 `catch (Throwable ignored)`**

项目里有 **46 处**静默捕获。大多数是合理的（清理、防御），
但已修过的三个 bug 都是从中来的。值得逐条判断：
**这里吞掉的异常，如果真发生了，用户会知道吗？**

### 优先级中

| 事项 | 说明 |
|---|---|
| 联网搜索走 Command Code | `/alpha/web-search` 端点**未验证**。若可用，可能免除 `DEEPSEEK_API_KEY` 依赖。注意这属于 DSH 侧插件能力，不是纯 App 改动 |
| 模型列表同步 | 从 `/provider/v1/models` 拉实时列表，自动更新模型配置 |

## 验证手段

**没有模拟器，没有真机调试回路。** 所有验证都靠下面这几种间接方式。
接手后请沿用，并继续补充。

### 能自动化的（每次构建都跑）

```bash
bash scripts/run_tests.sh     # 423 项纯逻辑断言
```

### 需要手工跑的

| 验证什么 | 怎么做 |
|---|---|
| **运行包完整性** | 拉线上清单，与本地逐分片比对 sha256 |
| **哨兵是否真实存在** | `tar --use-compress-program=unzstd -tf <分片>` 里找 |
| **补丁前提是否成立** | 从线上运行包提取目标文件，grep 匹配标记 |
| **生成的 YAML 是否合法** | 拿它**真的启动一次 DSH**，看插件是否被加载 |
| **归档能否正确解压** | 用 App 自己的 `unpack.js` 解压，与直接 tar 比对文件数 |
| **恶意备份包** | 构造带 `../` 的 zip，确认磁盘上**真的没有**多出文件 |

### 起一个临时 DSH 验证插件

```bash
export DSH_HOME=/tmp/probe
node --expose-internals <dsh>/lib/bin.js --profile web --no-open --port 3099
# 取日志里的 token，然后：
curl -sSL -o /tmp/index.html "http://127.0.0.1:3099/?token=<token>"
grep -o '<插件名>' /tmp/index.html      # 出现即说明插件生效
```

这个「检查首页里有没有插件名」的方法，是唯一能确认
bundle 类插件真的生效的方式。

## 接手时建议的第一步

1. 读 `AGENTS.md`（红线与约定）
2. 读 `docs/ARCHITECTURE.md`（架构与机制）
3. 读 `docs/GOTCHAS.md`（踩过的坑）
4. 跑一遍 `bash scripts/run_tests.sh`，确认基线是绿的
5. 跑一遍 `bash scripts/build_bootstrap.sh`，确认能构建出 APK
6. 然后从「待办 → 优先级高」里挑一件开始

**改动前的自检**：

- 这个改动会影响启动路径上已有的行为吗？
- 有没有纯逻辑可以抽出来测？
- 失败的时候，用户会知道吗？（还是又一个静默失败）
