用户报告电脑约 200 tok/s、手机不足 80。本次使用同一现有账号、DeepSeek V4.1 Flash、Max 和 1M 预算，在同一台 Mac 的网络上对比桌面与独立 ARM64 Android 15 模拟器。模拟器不能代表用户 Android 17 真机的温度、存储、网络或已有会话。

| 链路 | 两轮速度（tok/s） | 验证边界 |
|---|---:|---|
| 桌面 Node 24.22.1 → 生产适配层 → 官方 CLI | 147、124 | 无聊天页面的独立新请求 |
| Android Node 26.4.0 → 同一适配层 → 同一 CLI | 114、123 | 模拟器独立脚本，root 执行，未经过 App UI |
| 正式签名 1.3.0 APK → 实际内核与 WebView | 150、121 | 两个新会话，聊天页实际显示值 |

三组均为 SDK 0.3.291 / CLI 2.176.0，使用相同的中文科普请求。独立脚本仅公布一个测试工具，完整 App 使用其真实工具集；两者的上下文不同，不视为完全相同的服务端负载。服务端生成内容和 token 数也不固定，不能把这些少量样本解释成确定的 Android 性能损失比例。

## 网络与代理约束

不修改用户既有代理规则，保留代理应用运行。模拟器无 VPN，系统 HTTP 代理为 `:0`；独立测试进程清除 HTTP/HTTPS/ALL_PROXY 并设置 NO_PROXY。既有路由的只读连接记录确认，测试 Node 与模拟器 QEMU 进程均命中 `direct` / `final`。代理配置的三个文件 SHA-256 在测试前后相同。官方系统镜像直接从 Google 下载并验证官方清单的大小与 SHA-1；APK、内核和四个工具归档均核对固定摘要。

## 结果与限制

- 没有复现固定低于 80 tok/s 的限制；实际 APK 在这两轮可达到 121–150。尚未定位用户真机差距的具体原因，不能宣称已修复该差距。
- DSH 聊天页速度为整个会话的累计输出 token / 累计解码时间。该时间从首个非空输出到 assistant 消息提交，包含 CLI 收尾，不能当成单轮瞬时速度。
- 独立脚本实测 CLI 在末个输出后还有约 0.5–0.8 秒收尾。完整 App 第二轮约 22.4 秒内，WebView 两个长任务合计 218ms、单次最大 109ms；这些样本没有支持持续两倍减速的界面阻塞证据。
- 后续对比应使用新会话、相近的实际输入量和输出长度，并读取细分运行日志。账号、模型、强度相同仍不能保证会话累计口径、实际工具/历史上下文和当次服务端速度相同。

## 全新安装发现的问题与修复

正式 1.3.0 的全新安装在第一次配置同步时，读取尚不存在的 `.dsh/settings.yaml.imported`，抛出 FileNotFoundException。为继续完成上述 1.3.0 测速，仅在隔离模拟器创建了空导入标记；这不是正式 APK 首次安装通过的证据。

1.3.1 在读取前判断文件存在，未导入时继续正常初始化；已经导入的用户模型目录保持原逻辑。回归执行生产 `prepareConfig`、文件读写和合并方法，覆盖干净安装、已有待导入配置、已导入目录保留、缺失导入记录后恢复。修复前可复现相同异常，修复后通过。

1.3.1 的 `[dsh-perf] codebuddy` 增加 `last`、`result`、`deltas`、`chars`、`outputMs`、`tailMs`。时间均为本次调用起点后的毫秒，`outputMs` 是适配层首次至末次收到文本/思考增量的跨度，`tailMs` 是末次增量至适配调用结束的时间，包含宿主处理和 CLI 收尾；它们不是服务端内部计时，也不改写聊天页速度。日志仅保留计数、阶段与结果，不含提示词、正文或凭据。
