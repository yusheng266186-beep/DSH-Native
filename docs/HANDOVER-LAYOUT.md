## 二、当前代码状态（务必先确认，不要凭这份文档想当然）

### 视口：已回退到 480

`src/dev/dsh/nativeapp/MobileLayout.java` 的 `viewportWidth()`：

```java
static int viewportWidth(int screenWidthDp) {
    int width = screenWidthDp > 0 ? screenWidthDp : 400;
    if (width < 480) return 480;      // 窄屏一律 480
    return Math.min(width, 1440);
}
```

**这是对的，不要再改小。** 理由见第四节坑 1。

### 全局 button 覆盖：已移除

```css
button{flex-shrink:0!important;}   /* 已删除，不要加回来 */
```

**这是错的，不要再加。** 理由见第四节坑 2。

### 响应式 CSS 现状

`patchHtml()` 注入的 `<style id="dsh-native-responsive">` 里现有 24 条规则，
其中与编辑器相关的 7 条**依赖 CSS Module 类名，实测匹配不到任何元素**：

```css
[class*=Attachment] button, [class*=Card] button { ... }
[class*=Card] [class*=name], [class*=Card] [class*=meta], ... { ... }
[class*=Card] [class*=body], [class*=Card] [class*=meta] { ... }
[class*=Card] [class*=icon] { ... }
[class*=thumbnail] { ... }
[class*=remove] { ... }
```

**它们是无效的，但目前无害**（匹配不到 = 不生效）。
要删可以删，要留也不影响。删除时请同步改 `tests/MobileLayoutTest.java`。

剩下有效的规则只作用于：`[role=dialog]`、`[data-shortcut-modal="settings"]`、
`textarea/input/select`、`pre/code`、`img/svg`、触控目标高度、减弱动画。

### 布局体检探针：保留可用

`src/dev/dsh/nativeapp/LayoutProbe.java`，页面加载后 1.5s 在**真实 DOM** 里
测量并通过既有 console 桥输出，App 日志里以 `布局体检:` 开头。

**它是当前唯一能拿到真实数据的手段，请用它，不要再猜。**

## 三、探针已经拿到的真实数据

设备 436dp / 物理 1200px，视口 400（0.33.6 时的状态），
两次运行结果一致：

```
视口宽: 400    命中条目: 437~440

方形按钮（w×h，d = |w-h|）：
  24×44  d=20  aria=自动换行     _action_1pq26_43
  24×44  d=20  aria=复制         _action_1pq26_43
  26×44  d=18  aria=-            wSkVaW_tab / wSkVaW_tabActive
  28×44  d=16  aria=更多操作     _button_1rv3m_2 _ghost_1rv3m_45 _sm_1rv3m_28 ...
```

**这些是消息气泡内的工具按钮**（自动换行、复制、更多操作、Tab）。
高度 44px 正常，宽度 24~28px 偏窄但不算严重变形。

### 探针的三个局限（重要）

1. **用户截图里的附件 × 与发送按钮根本没被报出来。**
   探针只看到了消息区按钮。原因未查明 —— 可能是它们在探针运行时
   尚未渲染（用户当时可能没传图/没输入文字），也可能筛选条件漏了。
   **复现步骤**：装好 App → 打开聊天 → **输入几个字让发送按钮出现**
   → **传一张图片让 × 出现** → 再看日志里的 `布局体检:`。

2. **只报了前若干条**（代码里 `slice(0,10)`），440 条命中里绝大多数看不到。

3. **类名是哈希短名**（`_action_1pq26_43`、`wSkVaW_tab`），
   不含语义词。这是 CSS Module 编译的必然结果，**任何按语义写的选择器
   都匹配不到**。不要试图用类名做选择器。

### 一个有用的例外

`aria-label` 是 React 属性，**编译后原样保留在 DOM 上**，是稳定锚点。
已知可用值：`移除图片 {文件名}`（附件 ×）、`自动换行`、`复制`、`更多操作`。
发送按钮尚未确认其 aria-label。

## 四、我踩的坑（请认真读）

### 坑 1：把视口改小 → 全局放大、内容偏少

**改动**：`viewportWidth()` 从「窄屏一律 480」改成「忠实屏幕宽度」，
436dp 的设备于是拿到 436。

**为什么错**：视口越小，同样的 CSS 像素占的物理宽度越大。

```
视口 480 → 400：元素整体放大约 1.20 倍，一屏可视内容少约 17%
```

用户的原话是「整个页面被放大、可视内容偏小」。

**教训**：视口过大会挤压个别组件，过小会放大一切 —— **两个方向相反，
而放大一切的影响面明显更大**。我当时只看到「数学上不再溢出」，
没算这笔账。**不要只算溢出，要同时算放大。**

### 坑 2：全局 `button{flex-shrink:0!important}` → 设置界面被顶乱

**改动**：为了修「方形图标按钮被压扁」，给**所有** button 加了
`flex-shrink:0` + `!important`。

**为什么错**：这是**全局元素选择器 + !important**，会压倒上游组件
自身的布局规则。用户反馈「设置界面被顶乱、多个功能点不动」。

**教训**：`!important` 的全局元素选择器是**跨组件的破坏性操作**。
为修一个局部问题而动全局，代价远大于收益。

### 坑 3：按源码变量名写 CSS 选择器 → 规则全部落空

**改动**：`[class*=remove]`、`[class*=thumbnail]` 等。

**为什么错**：源码里的 `ComposerAttachments_module_css_default.remove`
是**编译前**的名字。编译后是 `_action_1pq26_43` 这种哈希短名，
**匹配不到任何元素**。而构建日志照样打印「已写入响应式布局」，
看上去一切正常 —— 这比明显报错更危险。

**教训**：验证 CSS 规则是否生效，**不能看它有没有被写进文件**，
要看它有没有命中真实元素。用探针。

### 坑 4：测试断言把错误做法固化成门禁

我一度用 `flat.contains("button{flex-shrink:0!important;}")`
断言这条规则**必须存在** —— 等于把破坏性改动写成了质量门禁，
以后谁想删都得先改测试。

**教训**：断言要守护**意图**（「不得有全局覆盖」），
而不是**实现细节**（「这条规则必须在」）。

### 坑 5：CSS 相关断言按整串匹配 → 假失败

拼接的 CSS 里选择器可能跨行拆开；而且压平空白会把属性值里的空格
也吃掉（`0 0 auto` → `00auto`），导致按整串匹配必然对不上。

**教训**：CSS 断言先压平空白再匹配，且模式串必须写成压平后的形式。
更好的做法是断言**语义**（规则存在与否的选择器意图），别抠字面。

### 坑 6：逐行删除 CSS 片段 → 生成语法非法的样式

为了清理无效规则而逐行删除，结果把多行规则拆散，产出
花括号不平衡的 CSS。

**教训**：改动拼接式 CSS **要么整体重写并校验语法**，
要么精确替换整块。不要逐行删。

### 坑 7（流程）：改完没发版 / 改了但没验证

- 有一次改完代码推送就报「已完成」，实际**漏了发版**，用户装不到。
- 有一次声称「已写入响应式布局」，实际规则一条都没命中。

**教训**：改动要分三段验证 ——
① 本地闸门（`check_java.py` + `check_source_hygiene.py`）
② CI（含 javac 与真实运行包消费验证）
③ 真机效果确认。**三段缺一不可，且第三段不能省。**

## 五、建议的下一步（按稳妥程度排序）

### 第 0 步：先确认基线

让用户装 **0.33.8**，确认两处回归（全局放大、设置顶乱）已消失。
**在拿到这个确认之前，不要再动布局代码。**

### 第 1 步：复现并采集真实数据

装好 App 后：
1. 打开聊天界面，**输入几个字**（让发送按钮出现）
2. **传一张图片**（让附件 × 出现）
3. 读日志里的 `布局体检:` 行

同时建议**临时扩大探针的输出量**（`LayoutProbe.script()` 里的 `slice(0,10)`
改成 40），并把筛选条件放宽，确保能覆盖到发送按钮与 × 按钮。

### 第 2 步：定点修复（不要碰全局）

拿到真实 className / aria-label / 尺寸后：

- 优先用 **`aria-label` 选择器**（如 `[aria-label^="移除图片"]`）——
  它是 React 属性，编译后稳定，比哈希类名可靠得多。
- 作用域要窄：只针对那一个元素，或其所在的直接父容器。
- **不要**写 `button{...}`、`[role=dialog] button{...}` 这类宽泛选择器。
- 一次只改一处，改完让用户确认，再改下一处。

### 第 3 步（可选）：重新评估视口

挤压的根因确实是「视口 480 > 屏幕 436dp」。
但**不要直接改小视口**（坑 1）。如果确实需要更宽的布局，
可以考虑的方向是让**特定区域**（如编辑器）使用更宽的布局，
而不是缩小整个页面的视口 —— 但这需要先确认不会重现「全局放大」。

「以为修好了其实没生效」这类问题，别跳过。
