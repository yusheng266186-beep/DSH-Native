## v0.23.5 —— 修「任务早结束了，通知栏还显示运行中」

v0.23.4 修好了「在跑却显示空闲」，但引入了反面问题：**状态会卡在运行中**。
这一版把状态来源整个理顺了。

### 原因（两个叠加）

**一、占位通知在骗人。**
前台服务启动时会先贴一条占位通知，原文案是「正在运行 · 展开通知可设置」，
而且没有计时器。如果之后没有任何真实状态推过来，它就一直挂着 ——
看起来就是「显示运行中，也没有工作的时间」。现在改成「正在获取状态」，
并且在页面加载完成后立刻推一次真实状态。

**二、我在 0.23.4 里让「页面按钮」也能决定运行状态，这是错的。**
`running` 是判断有没有任务在跑的唯一权威依据，来自 DSH 自己的会话列表。
但 **DSH 自己请求这个接口的频率极低**（实测一次启动只请求一两次），
于是我加了一个"第二证据源"：读页面上的「停止生成 / 发送消息」按钮。
问题是那两个按钮的文案匹配一旦失效就解析不出东西，而**误命中时会把状态钉死** ——
你遇到的就是这个：对话早已结束，按钮判断仍说"在跑"，而且它优先级最高，
把正确的信号盖掉了。

### 改法

1. **运行/空闲只认会话列表**（页面侧解析完整 JSON 的计数）。
   页面按钮不再参与运行状态判断，只保留一个用途：识别「等待批准」。
2. **自己定时重放会话列表请求**（每 5 秒）。
   记录 DSH 发过的那个只读 RPC 请求，用新的 rpcId 重放，响应由注入脚本自己接收。
   这样就不再受"DSH 什么时候才请求"的影响 —— 证据永远是新鲜的。
3. **状态卡住时要如实说**：超过 90 秒拿不到权威数据，报「状态未知」，
   而不是把旧状态一直挂着。通知里显示错误的状态比不显示更糟。
4. **加了状态诊断日志**：`[状态] 会话列表=… 页面=… → 通知栏=…`。
   状态一旦再算错，日志里直接能看到三个值，不用再猜。

### 现在的判定规则

| 会话列表 | 通知栏 |
|---|---|
| 有会话 `running:true` | 运行中（带计时器） |
| 全部 `running:false` | 空闲 |
| 页面出现「等待审批」 | 等待批准（高优先级提醒） |
| 超过 90 秒拿不到数据 | 状态未知 |

安装：通知栏 →「设置」→「检查 App 更新并安装」。
